# Zenith First-Customer Delivery SOP

Use this after an Operations Automation Sprint is accepted.

## 1. Confirm Scope

Before implementation, confirm:

- One workflow
- Intended outcome
- Deliverables
- Exclusions
- Fixed price
- Payment schedule
- Delivery window
- Success criteria

Do not start while scope is vague.

## 2. Understand the Existing Process

Document:

- Inputs
- Main steps
- Outputs
- Manual handoffs
- Repetitive work
- Common failure points

If the process cannot be explained clearly from start to finish, return to discovery before building.

## 3. Build the Smallest Useful Version

Prefer:

- Simple interfaces
- Few dependencies
- Clear error handling
- Easy backup/export where relevant
- Existing customer tools when practical

Do not add speculative features outside the agreed outcome.

## 4. Test

Before delivery:

- Run representative examples
- Test normal use
- Test obvious bad or missing input
- Verify outputs
- Check the original success criteria

## 5. Handoff

Deliver:

- Working solution
- Short walkthrough
- Simple operating instructions
- Known limitations
- Defined support window

The customer should be able to perform the improved workflow without Zenith operating it for them.

## 6. Close the Sprint

After acceptance:

- Collect remaining payment
- Record the result
- Capture measurable improvement when available
- Ask permission for a sanitized case study
- Ask for a testimonial if appropriate
- Note possible future workflows separately

New workflow means new scope.

## 7. Internal Review

Record:

- Why the project sold
- Actual effort
- Where scope changed
- Reusable components
- Objections encountered
- Pricing/process lessons

## Core Rule

The first project should prove that Zenith can find one expensive manual problem, improve it professionally, get paid, and create evidence that makes the next sale easier.
